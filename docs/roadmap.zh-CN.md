# 生产架构路线图：从 150 条到 1000 万条

## 1. 检索层扩展

1000 万条 1536 维 float32 向量，原始向量约 61GB；HNSW 图结构通常还会增加
1.5～2 倍内存。单机 PostgreSQL 不能直接承载，需要容量规划和分层。

建议：

- 使用 `halfvec` 或量化向量，在可接受的召回损失内降低内存。
- 按租户、卡种、生效年份分区，把活跃政策放在较小分区。
- 查询走只读副本，写入和重建走独立路径。
- 离线构建 HNSW/IVF 索引，使用蓝绿索引切换发布。
- 只对变更文档重新 embedding，避免全量重建。
- 当单集群无法满足 P99 或召回目标时，再引入独立向量检索服务。

每次调整 ANN 参数，都要在固定样本上对照精确检索，同时记录召回、构建时间、内存、
P50/P99，不能只看延迟。

## 2. 数据时效与缓存

政策文档需要 `effective_from`、`effective_to`、`supersedes`、`status` 和
`version`。检索时按生效窗口过滤，默认选权威版本，历史查询可以显式选择旧版本。

- 政策变更走消息队列或 outbox，不做全量重建。
- Redis 缓存 key 使用“规范化查询 + 过滤条件 + 索引版本 + 模型版本”，TTL 5～15 分钟。
- 政策发布事件触发缓存失效，避免旧答案继续命中。
- 高频问题可以预计算向量和候选结果。
- 金融场景优先使用精确缓存；语义缓存需要单独审计，风险更高。

## 3. 治理、PII 与访问控制

知识库是政策文本，但客户问题可能包含卡号、账号、地址等敏感信息。

- 在 embedding、日志和第三方 API 调用前做 PII 脱敏或 token 化。
- 文档级 ACL 与 PostgreSQL Row Level Security 结合，禁止跨租户检索。
- 审计查询、召回文档 ID、模型版本和政策版本，但不记录原始 PII。
- 传输和静态存储加密，密钥由 KMS 管理并定期轮换。
- 使用外部 embedding/rerank 前完成 DPA 和数据驻留评估。
- 把召回文本视为“证据”，不要当作指令；生成层必须引用来源并拒绝无依据回答。
- 监控 prompt injection、数据外泄和异常检索模式。

## 4. 服务等级目标

建议把指标拆开：

- 向量候选检索：P99 < 100ms。
- 混合检索 + 重排序：单独报告端到端 P50/P99，Cross-Encoder 通常是主要成本。
- 答案生成：关注首 token 延迟，但不能牺牲引用正确性。

需要监控：政策更新后的召回漂移、空结果率、过滤回退率、重排序分歧、各卡种/分类的
检索质量，以及 embedding 服务的 GPU 利用率和排队时间。
